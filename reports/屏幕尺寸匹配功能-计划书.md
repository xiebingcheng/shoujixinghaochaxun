# 「按屏幕尺寸找替代箱号」功能 · 计划书

日期：2026-10-13
状态：**方案评估阶段，尚未改动任何代码**

---

## 一、结论先说

**可以实现，但功能的定位要摆正：它只能做「相近尺寸候选箱号推荐」，不能做「可以通用 / 可以替代」的自动判断。**

原因很简单：屏幕尺寸只是"能不能凑合用"的**必要条件之一，不是充分条件**。同样 6.7 英寸的两块屏幕，长宽比、排线走向、开孔位置、屏体类型不一样，照样装不上。所以这个功能的正确形态是：

- 用户搜一个型号 → 系统给出「屏幕尺寸最接近的几个箱号」；
- 店员拿着这份候选清单，**现场比对实物**，能用就成交；
- 页面上全程不出现"可替代""通用"字样，避免客户以为一定能装。

一句话：**它是"缩小翻找范围"的线索工具，不是"自动判定能用"的决策工具。**

## 二、现在的家底（基于当前数据实测）

| 项目 | 数值 | 说明 |
|---|---|---|
| 上线箱号 | 129 个 | S / L / Y 三种前缀 |
| 型号条目 | 2510 条 | 含同一型号出现在多箱的重复 |
| 去重型号 | 1774 个 | 这是新功能真正要处理的规模 |
| 只出现在一个箱子的型号 | 1146 个（64.6%） | 这些型号一旦缺货，**确实没有现成的同款箱子可查** |
| 屏幕尺寸相关字段 | **0** | 6 个原始 xlsx 只有「箱号 / 商品名称 / 型号」三类列，没有任何尺寸信息 |
| 已有人工替代关系 | 18 对 | `docs/data/substitutes.json`，人工核实、最可信 |

两个关键判断：

1. **现有数据里一条屏幕尺寸都没有**，所以本功能的真正难点不在"匹配算法"，而在"屏幕尺寸数据从哪来、怎么保准"。算法部分反而是小工作量。
2. 近 2/3 的型号是"独苗箱"，这正好说明你要解决的是真实痛点；但也说明尺寸匹配会经常被用到，**数据错误的影响面很大**——推荐错箱子比不推荐更伤客户信任。

## 三、为什么单靠"屏幕尺寸"不够（这一步决定了功能怎么做）

判断一块屏幕总成能不能装到另一台机上，实际取决于至少 6 件事：

1. 对角线尺寸（英寸）——你提到的、也是目前唯一能低成本拿到的；
2. **长宽比 / 屏幕比例**（16:9、18:9、19.5:9、20:9…）——同样 6.7"，比例不同，实际长宽能差好几毫米，直接决定装不装得进框；
3. 分辨率（1080×2400 和 1080×2340 驱动不一样）；
4. 屏体类型（OLED 硬屏 / 软屏 / 柔性、LCD）——影响厚度和贴合；
5. 外形（水滴 / 刘海 / 挖孔 / 直屏 / 曲面）；
6. **排线位置、长度、FPC 接口**——这条最要命，尺寸完全一样的屏也可能因为排线方向不对而装不上。

所以设计上做一个务实取舍：

- **系统负责**：尺寸 + 比例，把候选范围从 129 箱缩到几个箱；
- **现场负责**：排线、开孔、屏型——就是你原本说的"现场再比对一下"。

给候选打一个 **"相近程度"** 分级，让店员一眼知道"这个更像"还是"这个只是碰碰运气"。

## 四、功能设计

### 4.1 用户看到的流程

1. 搜一个型号（例如客户要 `红米10A` 的屏幕）。
2. 系统查这个型号的屏幕尺寸（假设 6.53"、20:9）。
3. 扫描所有箱号，找出箱内**有尺寸接近机型**的箱子。
4. 结果页在原有的「精确匹配 / 相近结果」之后，多出一组：
   **「屏幕尺寸相近的箱号（仅供参考）」**
5. 每张候选卡片显示：
   - 箱号 + 箱名；
   - 箱内**尺寸最接近的那个型号**及其尺寸（例：`红米9A · 6.53″`）；
   - 与目标型号的尺寸差（例：`差 0.00″，同比例`）；
   - 一个"相近程度"标记（见 4.3）。
6. 页面固定一句提示：**「屏幕尺寸相近 ≠ 可直接通用，请现场比对尺寸、比例、排线、开孔后再确认。」**

特别处理一种情况：**目标型号在全库完全没有记录**（就是你说的"没覆盖的型号"）。这时原来的页面只会说"没找到"，新功能要变成：

> 没找到这个型号，但以下是屏幕尺寸相近、可以现场试试的箱号 →

这恰好是最能挽回生意的场景。

### 4.2 匹配算法（草案）

对查询型号 `M`（尺寸 `S`、比例 `R`）和候选箱号 `B`：

- 取 `B` 箱内所有有尺寸数据的型号，算尺寸差，取最小的那个作为**代表型号** `m*`；
- `d = |尺寸(m*) − 尺寸(M)|`；
- 比例 `R(m*)` 是否等于 `R(M)`，作为第二判据。

### 4.3 相近程度分级（建议值，后续可用真实数据校准）

| 级别 | 条件 | 颜色 | 含义 |
|---|---|---|---|
| A 尺寸一致 | `d ≤ 0.05″` 且比例相同 | 绿 | 最值得优先试 |
| B 尺寸接近 | `d ≤ 0.15″` | 黄 | 现场比对，大概率能试 |
| C 勉强候选 | `d ≤ 0.30″` | 灰 | 只是给个方向，成功率低 |
| — | `d > 0.30″` | 不显示 | 差太多，不给假希望 |

阈值先用经验值，上线后用真实成交/失败记录回头校准（第五节的回测能帮忙定阈值）。

### 4.4 排序规则（从高到低）

1. 相近级别（A → B → C）；
2. 尺寸差 `d` 从小到大；
3. 比例是否一致（一致的往前放）；
4. 是否同品牌 / 同系列（同系列排线更可能接近）；
5. 命中数多的箱子靠前。

### 4.5 和现有「可替代箱号」的关系（很重要）

现在已经有 18 对**人工核实过**的箱号替代关系，这是最可信的。

- 人工核实的 → 继续用「**可替代**」标记，措辞不变；
- 尺寸匹配出来的 → 用「**尺寸相近**」标记，措辞、颜色、分组都区分开。

**绝不把自动推荐混进人工确认的那一组**，否则店员会以为"这也是核实过的"，一次装错就毁掉对这个工具的信任。

排序上：人工替代永远排在尺寸匹配的前面。

### 4.6 箱号"代表尺寸"兜底（可选增强）

给每个箱子也记一个代表尺寸（取箱名对应机型，或箱内型号尺寸的中位数）。好处：

- 搜一个只有箱名、型号没覆盖的箱子时，也能给它一个尺寸；
- 浏览列表里可以直接按尺寸筛（未来做"只要 6.1 寸的箱子"这种筛选）。

## 五、屏幕尺寸数据从哪来（本功能 80% 的工作量在这里）

这是决定成败的一步：**数据表不准，功能就是负资产。**

### 5.1 需要的字段

每条记录建议存：`型号规范 key → { 英寸, 比例, 分辨率(可选), 来源, 置信度 }`。

### 5.2 三步走

**第 1 步 · 建基础尺寸库**

优先用**中文手机库**（中关村在线、太平洋等），因为箱内型号本身就是中文写法（`华为Nova12Pro`、`红米10A`），匹配比英文库容易得多；GSMArena 作为补充。

**第 2 步 · 型号归一 + 自动匹配**

复用现有的 `norm / core` 逻辑（`tools/build_data.py` 和 `docs/assets/search.js` 里已有），把 1774 个箱内型号映射到基础库。

难点是**没有品牌前缀的短码**（`Y10`、`A11`、`S50T` 这类，实测约 497 个，占 28%）。解决办法：

- 用**箱名推断品牌**（实测 129 个箱名里 85 个能直接看出品牌，例如 `S16 → OPPO A11X`），再补上前缀去匹配；
- 用同箱内其它型号的品牌分布交叉验证。

**第 3 步 · 人工补漏**

脚本自动生成**「待补尺寸清单」**（按箱号分组），人工逐条填。自动匹配大概能覆盖主流机型，剩下的靠人工补。

### 5.3 覆盖度目标与报告

- 目标：**80% 以上的箱内型号**有尺寸数据（主流机型占大头，达标不难）；
- 生成报告 `reports/屏幕尺寸覆盖报告.md`：缺数据的型号清单、按箱号分组、覆盖率百分比；
- 数据文件和现有做法保持一致：手工可编辑的 JSON，`build_data.py` 不覆盖；
- 每一条都记清"来源 / 是自动还是人工"，方便以后追溯错误。

### 5.4 工作量估算

| 事情 | 预估 |
|---|---|
| 尺寸库抓取 / 整理脚本 | 1 天 |
| 自动匹配 + 覆盖率报告 | 0.5 天 |
| 人工核对与补漏（约 500～700 个型号） | 5～8 小时（按 100～150 条/小时） |
| 匹配算法 + 前端 + 小程序 | 1.5～2 天 |
| 回测与调参 | 0.5 天 |

## 七、强烈建议：先做 3 天小实验，再决定要不要全量投入

在动手补 1774 条尺寸数据之前，先花很小的成本验证核心假设——**"尺寸接近的箱子，人工核实过的替代关系里是否真的成立"**。

用现成的 18 对人工替代箱号（`S44-S04`、`S49-S33` …）做实验：

1. 人工查这 18 对箱子里**箱名代表机型**的屏幕尺寸；
2. 看人工认可的"可替代"关系里，尺寸差到底有多大；
3. 结论：
   - 如果绝大多数 ≤ 0.15″ → 假设成立，阈值有据可依，放心全量做；
   - 如果差异很大 → 说明"尺寸"这个信号太弱，要重新想（比如改用"箱内主流型号的尺寸分布"或干脆扩大人工替代表的维护）。

这一步只要几小时，但能避免"做完一千多条数据才发现方向不对"。

## 九、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 尺寸数据录错 | 推荐错箱，客户/店员失去信任 | 每条记来源；抽样核对；分级显示而不是一口咬定 |
| 型号短码重名（如 `Y10` 在多品牌都有） | 匹配到错的尺寸 | 用箱名/箱内品牌推断品牌后再匹配 |
| 忽略屏幕比例 | 同尺寸但装不进 | 比例作为第二判据，比例不同的降级显示 |
| 店员把"尺寸相近"当成"可替代" | 退货纠纷 | 措辞、颜色、分组三处区分；固定免责提示 |
| 覆盖不全，搜不到候选 | 功能像坏的 | 覆盖率报告兜底；没数据时明确说"暂无尺寸数据"，而不是沉默 |

## 十、验收标准

1. 覆盖率：≥ 80% 的箱内型号有屏幕尺寸；
2. 回测：用 18 对人工替代关系测试，其中"尺寸相近"的命中率达到预期（Phase 0 后确定具体数值）；
3. 精确匹配的搜索结果**完全不受影响**（原有功能零回归）；
4. 无尺寸数据时的提示明确、不误导；
5. 网页版与小程序版结果一致。

## 附：一句话总结

**能做，但要做成"缩小范围的线索工具"，而不是"自动判定能用"。真正的成本在屏幕尺寸数据本身，所以先用现有的 18 对人工替代关系做个小实验验证方向，再决定全量投入。**
